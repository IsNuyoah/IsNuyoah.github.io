第一轮 · HTTP、枚举与证据判断

01 · URL 与请求

题目

浏览器首次打开：

https://lab.example/app/?lang=zh#/reset?name=test

实际发给服务器的请求路径和 Query 分别是什么？页面显示“403”时，你会查看什么证据，判断究竟是哪次请求、哪个环节返回的？

标准答复

首次文档请求的路径为 /app/，Query 为 lang=zh；可写成 GET /app/?lang=zh HTTP/1.1。# 后的 /reset?name=test 整体属于 fragment，不随这次 HTTP 请求发送给服务器。前端脚本可以读取 fragment 并另发 API 请求，必须与首次文档请求区分。

看到页面显示 403 时，在浏览器 Network 中定位对应请求，记录 URL、方法、实际状态码、请求发起者、重定向链、请求携带的认证信息和响应头/正文。判断是文档请求、后续 API 请求返回了 403，还是前端自行展示错误文字。若要进一步区分代理、WAF、应用等环节，需结合可靠日志或受控对照；仅凭页面长度或一个响应头不能定论。

参考：https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Fragment

02 · 编号资源与越权

题目

/data/0 到 /data/3 返回 200，其他编号多为 302。现在能确认什么？要证明 IDOR/BOLA，还缺哪些关键证据？

标准答复

目前只确认这些编号在当前请求条件下返回 200，其他编号多返回重定向；需检查正文是否确为对应资源，并查看 302 的 Location 和后续结果。不能仅凭状态码证明对象存在、授权正确或发生越权。

验证 IDOR/BOLA 应先确认身份 A/B、对象分别属于谁、应用预期允许谁读取。选取已知属于 B 且按规则不应向 A 开放的对象，用 A 的有效会话请求它，并与 B 的正常访问和必要的匿名对照比较。若 A 实际得到 B 的受限对象内容，才有未经授权访问的证据。公开资源或按规则共享的资源不构成这种越权。

参考：https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/05-Authorization_Testing/04-Testing_for_Insecure_Direct_Object_References

03 · Touch 的响应差异

题目

随机路径为 302、长度 0，/api 为 403，/api/status 为 200，GET /api/scan 为 405；工牌登录返回 HTTP 200，正文却是 success:false

分别怎样解释？能否据此判断整个 API 树的权限，或认为工牌登录成功？

标准答复

随机路径 302、正文长度 0 表示这次响应要求重定向且无正文，需检查 Location。统一路由、认证处理等都是候选解释，不能仅凭此判断路径是否存在。

/api 的 403 表示该请求被拒绝；若同时有认证错误正文，它支持认证相关拒绝，但仍不能据此确定所有访问规则。

/api/status 的 200 表示该请求按 HTTP 语义成功，需结合正文判断返回了什么；不证明已经登录或拥有其他接口权限。

GET /api/scan 的 405 表示该目标不允许 GET，可查看 Allow 响应头了解声明的方法；不保证换方法就能通过认证或完成业务。

工牌接口 HTTP 200、success:false 表示 HTTP 层面的成功响应承载了业务失败结果，不能视为登录成功。原因要依据 error、正常流程及必要的日志判断，不能凭空增加一种认证机制。

不同路径、方法和身份可能有不同授权规则，因此不能将单个结果推广到整个 API 树。是否获得会话与授权访问，应结合实际认证结果及后续受保护资源验证；没有新 Set-Cookie 也不能单独判定所有会话状态。

参考：https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status

04 · 枚举结果是否可信

题目

为什么随机路径也返回 302/0 会让 Gobuster 的默认枚举遇到问题？过滤所有零长度响应可能漏掉什么？

标准答复

目录枚举通过候选路径的响应寻找差异，工具通常先探测随机路径。在本次只排除 404 的配置下，随机路径也返回会被保留的 302/0，说明当前筛选条件无法区分背景响应与潜在命中；对应版本的 Gobuster 因此在预检查阶段中止并提示调整过滤。这个报错本身不证明遭到限速或丢包。

排除长度 0 会同时隐藏所有零长度响应，包括真实路径的重定向、受保护入口及其他有效的无正文响应，并非只影响 302。无命中只表示当前词表、身份、请求方式、过滤条件及成功收到的响应中，没有留下候选结果，不能证明没有目录或接口。

补充原题：4614 次请求中 4599 个 errors，约 99.7% 未获可用扫描结果；不能将这些错误计作路径不存在，也不能视为完整枚举。

诊断时先暂停扫描，重复访问已知页面并记录延迟、状态和错误；再用同一小词表、相同超时等条件，仅降低并发，比较错误率与已知页面响应。必要时另开一组仅调整超时的对照。改善只支持相关因素影响，不足以单独确定是限速、服务负载还是链路故障；进一步归因需具体错误、响应或日志证据。

参考：https://github.com/OJ/gobuster/blob/master/gobusterdir/gobusterdir.go

05 · 上传与代码执行

题目

上传的 JPEG 与回读文件 SHA-256 一致，Exif 注释也保留了。这能证明什么、不能证明什么？要判断上传是否能导致命令执行，还缺什么证据？

标准答复

在本次测试中，相同 SHA-256 强烈支持上传与回读的文件字节一致，Exif 检查同时确认该注释被保留。结论限定于这次返回的文件，不能推广到服务器内部的全部处理过程。

它不能证明服务器完全未解析、扫描或处理副本，也不能证明存在或不存在命令执行。图像中包含一段代码不会自动使它执行。

判断上传能否导致命令执行，需要建立“可控上传内容或文件名 → 实际处理组件 → 可触达的执行点”的数据流证据，并核对触发方式、解释器或 shell 调用、权限和过滤条件。再用授权环境中的无害、唯一标记验证实际执行及其因果关系，并排除仅存储、回显或普通资源请求等解释；不以文件能上传、能下载代替执行证据。

06 · 加密、哈希与密钥

题目

某应用数据库存有一段无法直接阅读的字符串 C。源码中的相关语句是 password = decrypt(C, key)，其中 key 从配置文件读取。

你依据什么判断这里采用的是可逆加密，而不是密码哈希校验？如果只能拿到 C，没有匹配的 key，也没有其他已知漏洞，能否直接调用 decrypt 恢复原文？成功解出这个应用的密码，是否就证明能用它登录同名系统账户？说明理由与还需什么验证。

标准答复

按题面语义，decrypt(C, key) 使用密钥还原并返回 password，支持这是可逆加密；实际审计需确认函数实现和返回值，而不只看名字或 key 变量。密码哈希校验通常是对候选密码按相同算法、盐和参数重新计算，再比较结果，不是解密取回原密码。在题设没有匹配密钥、没有其他已知漏洞的条件下，不能仅靠调用 decrypt 恢复原文。

解出应用使用的密码，也不能证明同名系统账户使用相同密码或允许登录。需核对账户、目标服务及认证方式，并在授权范围内用该凭据进行当前认证验证；成功结果应确认实际身份和对应服务。认证失败也可能与账户策略等因素有关，不能只凭一次失败断言密码错误。

参考：https://cryptography.io/en/stable/fernet/ （作为带密钥解密的实例，不据此推断题中采用 Fernet。）

07 · 流量中的认证与当前状态

题目

昨天的抓包在同一个 FTP 控制连接中显示：

客户端 → 服务端：USER trainee
客户端 → 服务端：PASS lab-example-password
服务端 → 客户端：230 Login successful

这三条记录能证明什么？能否证明这个密码今天仍有效，或者同一用户名可以用它登录 SSH？如果要确认这些推测，分别需要什么证据？

标准答复

同一 FTP 控制连接中的 USER/PASS 显示用户名和口令在该抓包中可直接阅读；随后 230 表示服务端报告该次 FTP 登录成功。它不能证明口令今天仍被接受，也不能证明 SSH 使用同一凭据。当前 FTP 有效性需由当前 FTP 的认证成功结果确认；SSH 复用需独立的 SSH 密码认证成功及身份确认，避免把已有密钥或其他认证方式的成功误当成密码复用。这些验证都应限定在授权目标和账户范围内。

参考：https://datatracker.ietf.org/doc/html/rfc959

08 · 从伪代码理解认证

题目

某测试服务的认证逻辑如下，+ 表示按顺序拼接字符串，所有字符串均按 UTF-8 编码：

expected = DEFAULT_HASH
if 参数中有 -a:
    expected = -a 后面的值
认证通过条件：SHA512(UTF8(输入密码 + 固定盐 S)) == expected

服务实际以 auth-service -a H 启动。

现在要离线验证一个候选密码 p：应计算什么、与什么比较，需要哪些已知数据？DEFAULT_HASH 是否还参与本次比较？若公式改为 SHA512(UTF8(S + p))，原来的验证方式能否原样沿用？不要求写工具命令或模式编号。

标准答复

先顺着赋值执行：expected 起初等于 DEFAULT_HASH，但启动时提供了 -a H，所以随后被覆盖为 H，DEFAULT_HASH 不再参与这次比较。

对候选密码 p，应计算 SHA512(UTF8(p + S))，并与 H 比较。需要候选 p、固定盐 S、当前参考哈希 H，以及题面规定的算法、拼接顺序与编码；实际代码还要统一摘要的表示形式，例如都使用相同格式的十六进制字符串。

例如 p = "cat"、S = "42"，先拼成 "cat42"，再把它编码为 UTF-8 字节，计算 SHA-512，最后比较是否等于 H。这是在检验候选，不是从 H 直接解出密码。

若公式改为 SHA512(UTF8(S + p))，应改成先盐后密码；上例输入变为 "42cat"。仍可使用 SHA-512，但不能原样沿用旧的拼接顺序，必须按新公式重新计算。

参考：https://docs.python.org/3/library/hashlib.html

09 · 上传与后续连接的因果判断

题目

你在抓包中看到一个上传 script.php 的 HTTP 请求，文件内容包含连接到 192.0.2.10:4444 的代码；之后又看到目标主机向该地址端口发起 TCP 连接。

仅凭这些信息，能否断言文件已被执行并获得 shell？你还会检查哪些关联证据，来区分“只是发生网络连接”与“确实有命令执行会话”？这些信息是否足以确定上传端点究竟缺少哪项安全检查？

标准答复

不能仅凭上传和后续 TCP 连接断言已经执行该文件并获得 shell。先核对连接源、目的地址与端口、时间关系，并寻找上传文件的实际访问或处理触发请求；关联相应 TCP 流，检查有无真实命令输入及与之匹配的输出、身份或目录等结果。仅有 TCP 握手、提示符文字或无交互数据的连接，不足以证明命令执行会话。

若在当前授权环境中验证，可以使用一次无害、带唯一标记的交互，结合响应与必要的服务端日志或进程证据确认执行及来源；历史抓包缺少这些证据时应保留不确定性，不能补写不存在的运行结果。即使会话已经确认，也不能单凭结果确定上传端点具体缺少扩展名、内容、存储隔离或其他哪一项安全检查，需要进一步检查请求/响应、配置、代码或受控对照。
