TryHackMe Domino 渗透测试笔记

一、目标信息与攻击链概览

这次练习的目标是 NexusCorp 员工门户。按照靶场提示，需要把多个小问题串联起来，逐步扩大访问权限。下面按照我的实际操作顺序记录测试过程，包括 SQL 注入测试、Session 结构分析和工单回连测试，以及这些测试如何帮助确定下一步方向。

项目本次记录
靶场TryHackMe · Domino
目标 IP10.146.180.198
本机 VPN IP192.168.129.1
Web 入口http://10.146.180.198/

The NexusCorp Employee Portal appears to be a typical internal application with authentication controls and role-based access in place. However, multiple small weaknesses, ranging from misconfigurations to logic flaws, can be combined to fully compromise the system.
As an attacker, your objective is to observe how the application behaves, interact with its endpoints, and identify weak trust boundaries. By analysing requests, modifying parameters, and chaining vulnerabilities together, you can progressively escalate your access and move deeper into the system.
A single misstep can trigger a chain reaction, exploit each weakness in sequence and watch the system fall, one domino at a time.

13.1 Web 身份认证与签名验证机制

Authentication 与 Authorization 分别解决什么问题？

Authentication（身份认证）回答“当前请求代表谁”，例如验证登录凭据或会话令牌。Authorization（授权）回答“这个身份能操作哪些资源”，例如普通用户能否读取管理员资料。登录成功之后，每个受保护接口仍需要执行授权检查。OWASP 授权指南

放到 Domino 中，Sarah 的登录是身份认证；Sarah 能否访问 id=1 的用户资料、能否调用文件接口，则属于授权问题。IDOR 的关键是服务端没有正确限制当前用户可访问的对象，不需要先成为管理员。

JWT 的 Header、Payload 与 Signature

这里讨论常见的 JWS 紧凑形式 JWT，而不是加密形式 JWE。它由点号连接三个部分：

部分常见内容阅读时关注什么
Headeralg、typ声明使用什么算法，例如 HS256
Payloadsub、exp、iat，以及自定义 role身份、有效期和业务声明；内容可被解码，不应直接视为可信
Signature签名或消息认证码的编码结果服务端是否真正验证了前两段的完整性

sub 通常标识主体，exp 表示过期时间，iat 表示签发时间。服务端应先按自身认可的算法和密钥验证令牌，再按应用要求检查有效期、签发者、接收者等声明，最后作授权判断。不能只读取 role 就放行。RFC 7519：JWT 声明、RFC 7515：JWS 结构与验证

HS256、HMAC-SHA256 与编码的关系

HS256 指使用 SHA-256 的 HMAC。HMAC 是基于共享密钥的消息认证码，签发方和验证方都掌握同一个密钥；它不同于 RSA 那类公私钥数字签名。JWT 中仍习惯把第三段称为 Signature。RFC 7518 `3.2：HMAC 算法

其计算关系可以写成：

Base64/Base64url 只是可逆编码，不需要密钥，也不保护完整性。HMAC 则要求密钥，目的是检测内容是否被篡改；它也不会隐藏明文。标准 JWS 的 Base64url 使用 -、_ 替代普通 Base64 的 +、/，并省略末尾 =。分析靶场中的自定义实现时，要核对实际采用的编码，不能默认它完全符合标准。RFC 7515：Base64url 与签名输入

Session Cookie 不一定是 JWT

Cookie 是浏览器携带数据的机制，Session 是应用维持会话状态的机制。常见方式是 Cookie 只保存随机会话 ID，用户资料存放在服务端；也有应用把身份数据与校验值一起放进 Cookie。另一个容易混淆的术语是浏览器的“会话 Cookie”：它通常指没有设置持久过期时间的 Cookie，而不是指定其中必须存放哪种认证格式。OWASP 会话管理指南

13.2 HTTP/1.1 报文结构与 Burp 请求调试

先看清报文边界，再判断业务响应

HTTP/1.1 请求由请求行、请求头、一个空行以及可选的消息体组成。下面是一个独立示例：

请求行中的三部分是方法、请求目标和协议版本。在线路上，请求行和各 Header 行通常以 CRLF 结束；最后一个 Header 后再接一个 CRLF，于是形成 \r\n\r\n，把头部与消息体分开。这里写出的 \r\n 是转义表示，不是要在 Burp Raw 中输入反斜杠和字母。RFC 9112：HTTP/1.1 报文格式

Content-Length 计算消息体的字节数，不包括请求行、Header 和分隔空行。示例消息体是 21 个 ASCII 字节，假定末尾没有额外换行。中文、URL 编码和末尾换行都可能改变字节数；修改请求体后要让 Burp 正确更新长度。HTTP/1.1 还可使用 Transfer-Encoding 确定报文边界，普通调试时不要随意混用两套长度声明。RFC 9112：消息体长度

Connection: close 表示本次交换后关闭连接，不代表“停止服务器中的程序”，也不是验证身份的字段。Cookie 与 Authorization 则可能分别携带不同认证凭据；本题的 Session 与 JWT 正是如此。

状态码要结合响应头和响应体一起看

状态码通常表示本题中的判断方式
200请求成功处理继续看响应体，确认是否真的返回了目标源码或页面
302重定向查看 Location；跳回登录页与跳到后台含义不同
400请求存在客户端错误先检查报文格式、参数和长度，不急于归因于权限
401缺少有效认证凭据检查认证头、会话状态和令牌是否有效
403服务端拒绝执行请求检查角色、资源权限及响应中的具体提示
404未找到目标资源，或服务端不公开其存在回连日志中的 404 仍说明该 HTTP 请求已经到达监听服务
500服务端内部错误只能说明处理异常，不能单凭它确认漏洞利用成功

以上是通用语义；应用可能使用自定义错误处理，所以状态码与正文需要相互印证。RFC 9110：HTTP 状态码

Raw 与 Inspector 是两种查看方式，不是两份独立请求

Raw 适合检查请求行、Header、空行及完整消息体；Inspector 会把请求头、Cookie、参数等拆成结构化字段，并可能自动解码展示。修改 Inspector 中的解码值后，应回到 Raw 查看最终编码和字段位置，避免把“显示出来的明文”误认为实际发送的字节。Burp 消息编辑器、Inspector 文档

本题可复用的 Repeater 调试顺序：

  1. 保留一份能正常工作的请求作为基线。
  2. 每次只修改一个因素，例如 id、JWT 的 role 或 Session 的前半段。
  3. 核对实际连接的主机、端口，以及 Host、Cookie、Authorization 等字段。
  4. 对比状态码、Location、响应体与耗时；必要时重发原请求，确认会话没有失效。

这样才能把“修改导致的结果”与“令牌过期、请求格式错误或服务波动”区分开。Burp Repeater 请求调试教程

13.3 Blind XSS 与 SSRF 的区别及验证方法

核心区别是代码在哪里执行、请求由谁发起

概念发生的位置需要观察的关键行为
存储型 XSS被保存的数据后来进入其他页面的可执行上下文浏览器把输入解释为脚本并执行
Blind XSS常见于测试者无法直接查看的后台、审核页面隐藏页面中的脚本执行通过外带信息体现出来
SSRF服务器或后台服务主动发起网络请求不可信输入影响请求目的地，跨越应用原本的访问边界

Blind XSS 常是存储型 XSS 的一种场景：“Blind”强调无法直接看到触发页面，并不意味着代码运行在服务器语言解释器中。SSRF 的关键则是服务器被诱导发起非预期请求；正常的链接预览或回调功能，不会仅因存在出站请求就自动成为 SSRF。PortSwigger：存储型 XSS、Blind XSS 测试、SSRF 原理与练习

为什么图片回连不一定等于 JavaScript 执行？

浏览器看到普通的 <img src="..."> 就可能加载图片，不需要执行自定义 JavaScript。onerror 则是资源加载出错时运行的事件处理代码，前提是页面确实把它解析成可执行的事件处理器，并且没有被过滤或浏览器策略阻止。MDN：资源 error 事件

后台机器人也可能有不同实现：一种会打开真实或无头浏览器，另一种只扫描文本里的 URL，再用 HTTP 客户端访问。因此，即使回连来源是靶机 IP，也不能只凭这一点区分“靶机上的浏览器”和“靶机上的 HTTP 客户端”；User-Agent 同样只是辅助线索。

怎样设计更有解释力的对照实验？

对照组设计思路可帮助区分什么
纯文本 URL只提交带唯一标记的完整地址后台是否会扫描或预览文本链接
普通图片地址仅设置 src，不放事件代码是否存在 HTML 渲染或资源预加载
需要求值的表达式完整回连地址只在 JavaScript 求值后形成是否存在脚本执行，而不只是完整 URL 提取
重复与基线测试每组用不同标记，等待相同审核窗口，再重复测试降低缓存、异步审核和偶发网络错误的影响

每次记录提交时间、工单编号、唯一标记、回连时间和请求内容。验证脚本执行时，可以使用测试者自己生成的标记或无敏感信息的计算结果，不需要收集其他人的 Cookie。

联系 Domino： 完整 URL 写法出现回连，而字符串拼接写法没有，支持“后台提取完整 URL 并主动访问”的推测。但两种写法还可能受到不同过滤规则影响，所以继续审计审核程序会更有说服力。若要进一步判断 SSRF，还要核实请求确实由服务端发起、目标地址是否受输入控制，以及这种控制是否越过功能允许的范围。这些属于对本次证据的分析，不等于新增了一条已经验证成功的漏洞链。

13.4 Linux 文件、目录权限与 Cron 提权原理

UID/GID 与文件所有权

UID 标识用户，GID 标识组。进程具有真实、有效等不同身份标识，并可能属于多个附加组；文件也记录所有者和所属组。查看权限时，要把 id 的结果与 ls -l 中的所有者、所属组和权限位对应起来，不能只看终端提示符。有效 UID/GID 等凭据参与权限判断；普通宿主机环境中的 UID 0 对应 root。Linux credentials(7)

同样的 rwx，对文件和目录含义不同

权限普通文件目录
r读取文件内容读取目录项列表，也就是列出名字
w修改文件内容修改目录项，例如创建、删除或改名；通常还需目录的 x
x允许作为程序执行，仍受格式等条件约束搜索、穿越目录，访问已知名称的子项

删除或改名主要操作的是父目录中的目录项，不等同于修改文件内容。访问一条路径时，还需要逐级通过中间目录的搜索权限。Linux inode(7)、path_resolution(7)

777 表示所有者、组和其他用户都有 rwx；1777 则额外设置了目录粘滞位。粘滞位通常限制只有条目所有者、目录所有者或有相应权限的进程才能删除、重命名该条目。它不等于“目录不能写”，也不会自动阻止修改一个本身允许写入的文件。inode(7)：特殊权限位

为什么本题不能改脚本，却能替换整个目录？

原脚本属于 root:devops，www-data 对它没有写权限。但 /opt 是无粘滞位的 777 目录，允许当前用户修改其下的目录项。本次通过在同一个父目录内把 monitoring 改名，再创建同名目录，使原路径转而指向自己的文件；不是把原脚本的所有者变成了自己。rename(2)：目录项重命名

这也说明，使用绝对路径并不足以保证安全：只要其中某一级目录可被低权限用户替换，高权限程序最终打开的对象仍可能变化。判断时应检查整条路径；例如 namei -l /opt/monitoring/health_report.sh 可以逐级展示路径组件。

13.5 反弹 Shell、TTY/PTY 与 Linux 进程控制

反弹 Shell 为什么能交互？

Reverse Shell 是目标端主动连接监听端，再把 Shell 的输入、输出接到这条连接上。网络连通后，监听端输入的字节可以成为 Shell 的命令输入，Shell 输出则沿连接返回。它解决的是通信问题，本身不会把普通用户提升为 root：本题第一次连接继承 www-data 的执行身份，后来由 root 定时任务启动的连接才具有 root 权限。

Linux 程序通常约定：

文件描述符名称常见用途
0标准输入 stdin读取输入
1标准输出 stdout输出正常结果
2标准错误 stderr输出错误与诊断信息

在本题 Bash 命令中，/dev/tcp/地址/端口 是 Bash 重定向支持的特殊语法，不一定是真实存在的磁盘文件。>& /dev/tcp/... 把标准输出和标准错误接到网络连接，0>&1 再让标准输入引用同一个已打开的连接。Bash：重定向说明

理解重定向还要注意顺序：

第一行先把输出接到文件，再让错误输出跟随它；第二行先让错误输出复制原来的输出去向，再改变标准输出，所以二者结果不同。

有 Shell，不代表有终端

TTY 指终端接口；PTY 是软件提供的一对伪终端端点。一个端点由终端程序控制，另一个为 Shell 等程序提供类似真实终端的接口，包括回显、行规程和终端信号等行为。单纯把 Shell 接到 TCP 字节流，不会自动建立这些终端能力。Linux pty(7)

因此，本题出现 cannot set terminal process group、no job control，与缺少适当的控制终端有关，不代表命令一定无法执行。bash -i 使 Bash 进入交互模式，也不等于创建 PTY。

Ctrl+C 究竟会中断谁？

在启用了相应终端处理的常见配置下，Ctrl+C 由终端驱动转换成 SIGINT，发送给该终端的前台进程组。程序可以处理或忽略某些信号，因此它不是无条件“强制杀死当前命令”。Bash：前台进程组与作业控制、Linux signal(7)

对简单的 nc 反弹连接而言，本机终端前台运行的可能是 nc。此时按 Ctrl+C 可能先中断本机 nc，导致整条连接断开，而不是只停止远端正在运行的命令。判断这类现象时，要先分清“本机终端—传输程序—远端 Shell”三层，以及哪一端正在处理控制字符。

为什么请求一直等待，或者会出现多次回连？

本题的 PHP 代码在命令执行调用中启动交互式 Shell，后者可能持续等待输入，使当前 HTTP 处理流程迟迟无法返回。请求未结束不等于没有触发，应该同时查看监听端。客户端断开连接也不保证服务端子进程立即结束，具体取决于进程关系和连接处理方式。

Cron 按调度时间触发任务，通常不会自动等待上一轮同一任务结束后才启动下一轮。如果任务长期阻塞，又没有锁或其他并发限制，后续周期可能启动新实例，因而出现多个进程或连接。关闭一次 Shell，也不等于修改后的定时任务已停止。这里是对执行机制的解释，本题具体出现多少实例仍应以进程与监听记录为准。cron(8)

13.6 PHP 文件处理与代码执行漏洞原理

同样接收“文件”，这些操作实际做的事情不同

操作主要行为数据何时变成代码
file_get_contents把本地文件或支持的 URL 内容读成字符串读取本身不会执行字符串中的 PHP
include包含文件并解析其中的 PHP 代码被包含内容进入 PHP 解释流程时
require包含行为类似 include，但失败处理更严格同样发生在解释被包含内容时
eval把字符串当作 PHP 代码执行字符串直接进入 eval 时

include 失败通常产生警告；require 在 PHP 8 中失败会抛出 Error，若没有处理会中断执行。两者的安全区别不在于谁“更适合接收用户输入”，而在于是否让不可信内容进入执行流程。PHP：file_get_contents、include、require、eval

LFI、RFI 与 RCE 不要只按参数名字判断

  • LFI（本地文件包含）：不可信输入影响了本地文件包含目标；影响可能是泄露内容，也可能在特定条件下进入代码执行。
  • RFI（远程文件包含）：不可信输入影响了远程内容的包含与解释。
  • RCE（远程代码执行）：描述最终能力，即远程输入导致目标执行可控代码；文件包含只是可能的实现路径之一。

如果只是 file_get_contents 读取文件并返回文本，更准确地说是文件读取或源码泄露，不能仅因读到了 .php 文件就认为 PHP 已被执行。本题则明确出现了“下载字符串后传给 eval”的链路。

Domino 的信任边界在哪里被跨越？

这里真正危险的转换发生在最后一步：外部响应原本是数据，却被当成了可信代码。str_replace 删除开头标记并没有净化代码；eval 通常本来就接收不带外层 PHP 起止标签的代码字符串。ob_start 与 ob_get_clean 只是控制输出缓冲，不是隔离执行的沙箱。PHP eval 语言结构

allow_url_fopen 与 allow_url_include 分别控制什么？

allow_url_fopen 控制可感知 URL 的文件流包装器，影响使用 HTTP 等 URL 的文件读取。allow_url_include 则针对 include、require 等操作使用 URL 的行为，并要求前者启用。它们作用的操作不同，不能互相替代。PHP：文件系统运行时配置、PHP：使用远程文件

因此，关闭 allow_url_include 并不能阻止本题“file_get_contents 获取内容，再 eval”的组合；而关闭 allow_url_fopen 也不是禁止 PHP 通过所有方式联网的总开关。根本修复方向是避免执行不可信字符串，对文件读取采用明确的允许范围。

还有一个与本题直接相关的细节：通过 HTTP 获取 rev.php，得到的是远端 HTTP 服务返回的正文。前面使用 Python 静态文件服务，返回的是文件中的 PHP 源码；如果提供文件的一端先解释了 PHP，目标拿到的就可能是执行结果，而不再是原始源码。判断远程代码链时，要检查实际响应内容，而不只看扩展名。

13.7 Linux 本地提权枚举结果的判断

枚举输出是候选线索，接下来要判断具体能力

本地枚举的目标不是收集越多输出越好，而是回答：当前身份能控制什么、哪个更高权限的进程会使用它、两者之间是否存在可验证的联系。

机制它提供什么不能直接得出的结论
SUID执行符合条件的程序时，有效用户身份可切换为文件所有者发现带 SUID 的系统程序就一定能获得 root
SGID可执行文件可影响有效组身份；目录上还影响新建文件的组继承SGID 一律等同于 root 权限
Linux Capabilities将部分特权拆分授予进程或程序只要存在 capability 就一定可利用
sudoers限制哪些用户能以哪些身份运行哪些命令允许一个命令就代表可以执行任意命令
Cron/其他任务按配置以某个身份运行程序每个定时任务都以 root 运行

SUID/SGID 还会受挂载选项、no_new_privs 等执行条件影响。Linux 也不会按普通原生可执行文件的方式兑现解释器脚本上的 SUID 位；因此不能只看 ls -l 中出现了 s 就结束判断。execve(2)：执行身份与限制、inode(7)：SGID

读懂 find 命令的范围

这条命令从根目录出发，只找普通文件，并匹配“包含 SUID 位”的权限。-perm -4000 中前面的减号表示指定的权限位必须存在，并非要求完整权限刚好等于 4000。-xdev 不向不同设备号的文件系统继续下探，所以独立挂载的数据目录可能不在这次扫描范围内；2>/dev/null 只是隐藏报错，不会让原本不可访问的目录变得可读。GNU find 手册

可以按需要补充 SGID 与 Capabilities 检查：

例如 CAP_SETUID 与变更用户身份有关，CAP_DAC_READ_SEARCH 与绕过部分文件读取、目录搜索权限有关。但还需检查它被授予了哪个程序、是否实际生效、该程序是否提供可控的对应操作，以及运行环境的其他限制。Linux capabilities(7)

sudoers 要看完整规则

sudo -l 用于查看当前用户可执行的命令；sudo -n -l 则不进行交互式密码询问。提示需要密码，只说明这次非交互查询无法继续，不能由此得出“机器没有任何 sudo 规则”。

若能读到规则，应一起查看目标用户/组、命令路径、允许的参数、NOPASSWD 标签以及环境限制。NOPASSWD 表示匹配规则的调用不要求密码，不会自动扩大规则原本允许的命令范围。sudoers(5)

pspy 与静态 Cron 枚举要互相印证

crontab -l 默认查看当前用户自己的任务，不代表所有用户的任务。还可检查有权限读取的 /etc/crontab、/etc/cron.d/ 等位置；看不到其他用户的 crontab，并不说明后台没有任务运行。

pspy 利用进程文件系统中的可见信息，并借助文件系统事件等方式增加捕获短生命周期进程的机会。它输出的 UID、PID、时间戳和命令行可以帮助定位高权限任务，但仍可能漏掉进程；没有输出不能等同于没有任务。pspy 项目原理与 Cron 示例

本题的判断链是：

  1. SUID 枚举暂未发现明显值得继续分析的异常项。
  2. /opt 权限表明普通用户可以影响该路径下的目录项。
  3. pspy 把 health_report.sh 与 root 执行身份联系起来。
  4. root_probe.txt 中的 uid=0 验证了替换后的脚本确实被高权限进程执行。

这些证据互相连接，才形成可解释的提权路径。对于以后遇到的其他枚举结果，也可以按“可控对象 → 使用它的进程 → 执行身份 → 实际效果”这四步继续判断。
