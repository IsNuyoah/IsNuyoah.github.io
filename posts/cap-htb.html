[HTB] Cap 渗透测试笔记

这次打的是 HTB 的 Cap（Easy / Linux）。实际链路包括 Dashboard 数据编号、抓包中的明文 FTP 认证、FTP/SSH 凭据复用，以及错误授予 Python 的 cap_setuid。

本文按实际发现顺序整理。Flag 与口令用占位符表示；

靶机重启后 IP 会改变。初始扫描使用 10.129.161.149；中间因为扫描原因reset了靶机，后续实际验证时使用 10.129.161.160。

路径概览

已验证的关键节点

01 · Dashboard 数据编号

枚举 /data/<id>，发现少数编号返回数据页，其余编号重定向回首页。

02 · PCAP 中的 FTP 明文认证

下载较大的抓包，在 Wireshark 中发现 FTP 控制流与成功认证记录。

03 · FTP 与 SSH 凭据复用

实际登录 FTP 取得 user flag，再验证同一凭据可登录 SSH。

04 · Python capability 提权

发现 python3.8 具有 cap_setuid；验证 UID 可切换为 0 后获得 root shell。

信息收集：扫描结果为什么不能直接下结论

最初对 10.129.161.149 使用了：

当次输出只显示 80/tcp，其余端口大多为 filtered。但扫描期间浏览器和 Nmap 都曾暂时失去目标可达性，停止后约一两分钟才恢复。因此这次只证明“高频探测时仅收到 80 的响应”，不能证明 21、22 等端口不存在。

后续在 Dashboard 网络连接表中可以看到：

  • 0.0.0.0:80 处于 LISTEN；
  • 0.0.0.0:22 和 :::22 处于 LISTEN，22 是 SSH 候选服务；
  • :::21 处于 LISTEN，后续以实际 FTP 登录验证该服务可用；
  • 127.0.0.53:53 仅绑定在 loopback，是本地 DNS stub；
  • 10.129.161.160:37680 -> 8.8.8.8:53 是出站连接使用的临时源端口，37680 不是监听服务端口。

LISTEN 才是服务端监听的证据；SYN_SENT、ESTABLISHED 等只是连接状态。高频扫描造成的丢包或临时不可达，也可能造成端口漏报。

Dashboard 数据编号与抓包下载

Dashboard 中存在 /data/1 一类路径。数字位于 path segment，而非 Query 参数；它可能是资源编号，但单凭 URL 不能直接断定是 IDOR。

对相邻编号做有限枚举后，0、1、2、3 返回 200，页面大小约为 17 KB；其余多数编号返回 302 并重定向至 /。这说明编号会影响所选数据记录，但尚不足以证明不同记录归属于不同用户。

其中 data/0 显示 72 个数据包，而 data/1 只有 2 个数据包。页面提供下载入口，因此优先检查包数较多的捕获文件。

总结与复盘

观察能证明什么不能直接证明什么
高频扫描只显示 80当时仅收到 80 的响应21、22 不存在
/data/0–/data/3 返回 200编号会影响所选数据记录已确认跨用户越权
FTP 中有 USER / PASS 与 230明文凭据泄露，且捕获时 FTP 认证成功该密码必然能用于 SSH
python3.8 带 cap_setuidPython 进程可能修改 UID当前环境一定能切换至 UID 0
uid=0 euid=0capability 在此环境中实际生效自动获得 root 的所有组身份或持久化权限

这台靶机最需要记住的不是命令本身，而是把“线索”和“已验证结论”分开：端口监听需要实际验证，捕获到的口令需要验证目标服务，file capability 也需要最小化测试后才能确认影响。

后续复盘的关键知识点

  1. 扫描可靠性与控制变量：--min-rate 5000 -T4 让目标出现暂时不可达时，不能把 filtered 当作“端口不存在”。复盘时应能说明：为什么降低速率、缩小端口范围、固定同一实例 IP，才有助于区分扫描漏报、服务异常和网络路径问题。

  2. 可枚举资源不等于已证实 IDOR：/data/<id> 返回不同内容，证明的是编号参与资源选择。要证明 IDOR/BOLA，还需要补足资源归属、当前身份以及服务端是否做对象级授权检查等证据。

  3. PCAP 的分析顺序：先从 Protocol Hierarchy、Conversations 找出应用层会话，再查看完整 TCP stream。FTP 控制连接中的 USER、PASS、230 分别说明什么，LIST、RETR 又为什么只是 FTP 操作而不是系统命令执行，应能独立解释。

  4. 凭据泄露与凭据复用是两次验证：抓到明文密码只证明它曾在某个协议中出现；230 证明 FTP 认证成功；只有实际 SSH 登录成功，才能证明该密码复用于 SSH。三个结论不能合并成一句“抓包拿到 SSH 密码”。

  5. SUID 与 file capabilities 的差别：SUID root 程序启动时会获得有效 UID 0；cap_setuid 则让进程能够调用改变 UID 的系统调用。本次还通过 uid=0 euid=0 验证了 capability 在实际执行环境中生效，而不是仅凭 getcap 输出下结论。

  6. 最小化验证与权限边界：先验证 UID/EUID 是否变为 0，再启动交互 shell，能把“配置异常”“能力生效”“获得 root shell”拆成独立证据。即使有效 UID 为 0，也应区分它与永久修改用户、获得所有附加组或持久化权限之间的差别。
