[HTB] Touch 渗透测试笔记

发表于2026-11-08|更新于2026-11-08|htb
|总字数:3.3k|阅读时长:12分钟|浏览量:

本文仅记录 Hack The Box 授权靶场。IP、账号、设备与凭据均属于实验环境；flag 不在正文重复展示。

本文按实际探索顺序记录。图片上传、CVE 查询和预订查询均做过验证，但没有成为入口；这些未走通的分支也保留在文中，以说明证据如何改变后续方向。

靶机信息

项目内容
平台Hack The Box
靶机Touch
难度Easy
系统Windows
初始实例10.129.164.242
重启后的实例10.129.169.42
完成情况已取得 user.txt 和 root.txt

靶机在练习中重新部署过。最初的端口扫描来自 10.129.164.242；后续 Web、RDP、kiosk 与提权操作在 10.129.169.42 上完成。

攻击路径

  1. 匿名 /api/status 泄露 DeviceHub 序列号，序列号可作为默认设备密码。
  2. 已认证管理页把设备凭据直接写入前端 HTML 的 onclick 参数，得到可用的 KioskUser RDP 凭据。
  3. RDP 进入受限 kiosk 后，关闭设备触发错误处理，借由 Support 链接打开 Edge，再经 file:/// 启动本地 cmd.exe。
  4. 以 KioskUser 获得反向 shell，从维护脚本中读取 MySQL root 凭据。
  5. MySQL80 以 LocalSystem 运行，且其 plugin_dir 对当前用户可写；加载 DLL 后收到 SYSTEM shell。

命令约定：TARGET_IP、ATTACKER_VPN_IP 和 MYSQL_ROOT_PASSWORD 均为需替换的文本标签。MySQL 密码必须紧跟 -p，即 -pMYSQL_ROOT_PASSWORD 中间不能有空格。

登录页是 Nexion DocReader（DeviceHub DH-100 — Gate B7），提供 Device password 与 Scan Staff Badge 两条路径。Layover 中的 Jenny Crawford 和 KS7X2M 曾被当作候选线索，但没有直接构成设备密码或 Windows 凭据。

HTTP 200 只表示服务正常处理了“没有检测到工牌”的业务请求；这次响应没有建立会话，也没有证明存在认证绕过。

API 枚举与 DeviceHub 登录

随机路径返回 302、长度 0，说明站点存在统一跳转基线。它不能表示所有路径不存在或都需要认证。根目录的 Gobuster 适合建立这一基线；本次需要递归检查 /api/ 时，改用支持 -d 深度参数的 Feroxbuster。

枚举排错与工具选择
  • Gobuster 仅排除 404 时，会把随机路径的 302/0 误认为有效响应而停止；加入 --exclude-length 0 后才可继续。
  • FFUF 使用 -t 80 -timeout 5 跑完 4614 个词条时出现 4599 个 errors。该结果只能说明大部分请求未得到可靠响应；尚未能将原因归为服务限速、高并发或 VPN。
  • Feroxbuster 首次把互斥的 --auto-tune 与 --auto-bail 同时传入，工具直接拒绝运行。修正后只保留 --auto-tune。
  • 早期曾把 /api 的 403 过度解读为必须先找到认证响应头才可继续枚举。随后通过状态、方法和响应差异继续检查，证明该判断不成立。

版本、CVE 与 localhost

Settings 页的 Firmware 1.4.2 与 Nexion Systems Service v4.2.1 是不同层级的版本。页面只有 Nexion 品牌，无法证实它与 Milesight 的 CPE 映射，故 vendor:milesight AND product:devicehub 不能直接视作当前靶机的漏洞结论；还需逐个核对候选 CVE 的厂商、产品和 affected versions。

Return to Kiosk 指向 localhost:5173。从 Parrot 浏览器访问时，localhost 指向攻击机本身，只能作为管理端与 kiosk 前端可能分离的架构线索。

总结反思

Touch 没有依赖一个单独的 CVE，而是把多处不安全设计连成了一条链：匿名接口泄露序列号，序列号又被当作默认密码；认证后的前端继续下发 RDP 凭据；受限 kiosk 的异常处理可启动浏览器和本地程序；最后，明文数据库凭据、宽松的插件目录 ACL 与 LocalSystem 服务身份共同放大为 SYSTEM 代码执行。

当时的观察这次记录留下的提醒
随机目录稳定返回 302/0先建立响应基线。大量超时和错误率较高的扫描结果不能直接当作目录枚举结论。
/api 返回 403，/api/status 返回 200同一命名空间内存在差异化访问控制；需要逐条用实际响应验证，而不能把一个路由的结果泛化到全部 API。
上传的 JPEG 回读后 hash 和 Exif 一致只能证明该文件原样存取；没有看到解析或执行 sink 前，不能把上传成功写成 RCE。
RDP 出现成功登录信息，随后传输超时凭据已验证有效，问题发生在会话建立后；超时的具体根因仍需另行证据。
root@localhost、可写 plugin_dir 与 LocalSystem 服务同时成立数据库权限、目录 ACL 与服务身份必须分别确认；三项缺一项都不能直接推出 SYSTEM 执行。

从防护角度看，设备序列号不应同时充当默认密码，设备和 RDP 凭据不应出现在 HTML 或 JavaScript 中。Kiosk 需要限制错误页、浏览器、file:// URI 与本地程序的调用链；MySQL 则应使用低权限服务账户、收紧 plugin_dir 的写权限，并从维护脚本中移除明文高权限密码。

参考与后续复习

后续复盘可按攻击链倒推：先解释为何 302/0 需要作为枚举基线，再区分“文件原样回读”和“文件被服务端解析”，然后梳理 kiosk 的 UI 限制为何没有覆盖浏览器与 URI 处理器，最后重新检查 MySQL 中“账户权限、文件系统 ACL、服务运行身份”三项前提如何共同决定影响范围。
