[HTB] Management 渗透测试笔记

发表于2026-11-02|更新于2026-11-03|htb

这次打的是 Management，一台 Linux Easy 靶机。我从首页的 SSO 入口开始，先折腾了前端资源解密、JATO 参数和匿名账户权限，后来通过 OpenAM 拿到 Shell，再沿着 GLPI 凭据和备份权限拿到了两个 Flag。中间也走了些弯路，一起记在这里。

解密前端资源

页面脚本说明 assets/app.enc 使用 Base64 包装，按这段加载脚本的格式，解码后前 12 字节为 AES-GCM IV，其余为密文和 authentication tag；页面中给出了 Base64 编码的 AES key。

第一次使用 HTTP 下载时得到 Nginx 301 Moved Permanently 页面。改用 HTTPS 并跟随重定向后，成功取得 Base64 文件，并使用 Node.js crypto 按 AES-256-GCM 解密，拆出前 12 字节 IV 和末尾 16 字节 authentication tag，生成 app.dec.js。

文件解出来了，但里面还是一堆 _0x... 形式的混淆代码。我当时没有从这里继续找到可用的接口或域名线索。

我也在浏览器 Console 中查看了解码后的内容，并复制保存为 app.dec.runtime.js。

OpenAM 漏洞探测与权限枚举

转向 JATO 参数验证

前端这条线暂时卡住后，我参考资料把方向转到了 CVE-2026-33439，关注点是 jato.clientSession 的 Java 反序列化处理。接下来先找目标上的对应入口，看看请求和响应有什么变化。

JATO 密码重置入口确认

在访问 /openam/ui/PWResetUserValidation 的正常密码重置流程中捕获到：

  • 方法：POST
  • Content-Type：application/x-www-form-urlencoded
  • 表单字段：PWResetUserValidation.fldUserAttr、PWResetUserValidation.tfUserAttr、PWResetUserValidation.btnNext、jato.defaultCommand
  • 当前请求包含 jato.pageSession，其值以 rO0AB 开头，符合 Java 序列化数据经过 Base64 编码后的特征。

这里能看到 JATO 表单和序列化会话参数，不过正常请求带的是 jato.pageSession，还不是我要检查的 jato.clientSession。两个参数不能混为一谈。

这一阶段按顺序做了五次参数验证。最明显的差异是：普通字符串被清空，而 HashMap 值会被保留。

顺序输入与位置观察结果
1POST 表单中的空值HTTP 200，密码重置错误与基线一致
2POST 表单中的字符串 A页面重新渲染空的 hidden input
3POST 表单中的序列化 Java String相同错误，hidden input 仍为空
4Query 中的序列化 HashMaphidden input 原样保留该值
5本地自定义 Comparator 的 PriorityQueue参数被清空，未复现本地触发输出

这一阶段尚不能确认 RCE。 参数被保留只是对象处理行为的线索；HTTP 200、页面长度变化和本地 Comparator 输出，都不能代替目标上的命令执行证据。

展开五次验证的请求与响应记录

随后在同一个 POST 表单中加入空的 jato.clientSession：

服务端返回 HTTP 200，并显示 The password cannot be reset for this user.，响应仍是密码重置页面。这次只是把参数放进 POST 表单发了出去；响应与基线一致，单凭 HTTP 200 看不出服务端是否处理了这个参数。

随后将 jato.clientSession 改为普通字符串 A。服务端仍返回 HTTP 200 和相同的密码重置错误，但响应长度增加，并重新渲染了空的 jato.clientSession hidden input。我能确认的是响应中该字段为空；究竟是输入被忽略、处理失败还是被归一化，仅凭页面还分不清。

随后使用合法 Java String 序列化值 rO0ABXQAD21hbmFnZW1lbnQtdGVzdA 作为 jato.clientSession 的 POST 字段。服务端仍返回 HTTP 200、相同的密码重置错误和空的 hidden input；当前结果未出现解析异常或命令执行。该测试仍携带了登录 Cookie，且参数位于 POST 表单中，不能作为预认证漏洞的最终判断。

随后将正常 jato.pageSession 的 HashMap 序列化值放入 Query 参数 jato.clientSession，并保持 POST 表单中的 jato.pageSession。服务端返回 HTTP 200，响应中的 jato.clientSession hidden input 原样保留该 HashMap 值，而普通字符串测试会被清空。该差异与目标接受符合预期结构的对象这一推测相符，但这次也改变了参数位置，尚不能隔离判断差异的原因；目前仍只是无害对象验证，没有执行命令。

随后将本地 PQTest$DemoComparator 序列化的 PriorityQueue 放入 jato.clientSession。服务端仍返回 HTTP 200，但响应把 jato.clientSession 清空，页面流程未改变。可能是目标缺少 PQTest$DemoComparator，也可能是类型检查或其他处理失败；没有服务端异常信息，还不能确定原因。这次没有在目标上复现本地 Comparator 的触发效果。

匿名会话权限枚举

使用已建立的匿名会话观察 Dashboard 请求，记录到以下结果（会话 Cookie 与 token 未写入）：

  • GET /openam/json/serverinfo/* 返回实例配置：realm 为 /，域名为 .management.htb，secureCookie=false、cookieSameSite=null、allowedWithoutReferer=true，自助注册和忘记密码功能关闭。
  • GET /openam/json/realms/root/users/anonymous 返回匿名用户资料。角色仅为 ui-self-service-user，状态为 Active，LDAP DN 为 uid=anonymous,ou=people,dc=management,dc=htb，universal ID 为 id=anonymous,ou=user,dc=management,dc=htb。
  • GET /openam/json/realms/root/dashboard/assigned 返回空分配结果：{"_id":"0","_rev":"0"}。
  • GET /openam/json/realms/root/users/anonymous/oauth2/applications?_queryFilter=true 返回 result: []，当前用户没有 OAuth2 应用。
  • GET /openam/json/users?_action=idFromSession 返回 400 Unrecognized request parameter '_action'，该请求尚未证明可用，需结合实际方法、路径和 API 版本继续核对。

匿名账户能进入 Dashboard，也能看到自己的资料和部分实例配置，但没有分配应用。我还没找到能从这里进入管理功能的办法。

API 文档权限观察

在匿名会话的 OpenAM Dashboard 帮助菜单中发现 API Explorer 和 API Docs，访问 API Docs 时显示 403 页面。我的账户只有 ui-self-service-user 角色，接下来就去看看这个 403 是在哪里拦下来的。

路由权限分析：

  • dashboard：要求 ui-self-service-user，匿名账户具备该角色，已实际访问。
  • oauth2Tokens：要求 ui-user，匿名账户当前没有该角色，预计会被拒绝，需以实际响应验证。
  • confirmLogin：要求 ui-user，属于登录确认流程。
  • continuePasswordReset、continueSelfRegister、loggedOut、loginFailure、sessionExpired：未声明 role，但它们是认证生命周期辅助页面，不是管理功能。实例 serverinfo 已显示忘记密码和自助注册均关闭，因此不能仅因缺少 role 就推断可利用。

当时我打算继续看 Dashboard 的 self-service API；OAuth2、密码重置和注册这几条线还没有验证出可用结果。

路由权限分析：

  • profile：要求 ui-self-service-user，匿名账户可以访问个人资料页面。
  • forgotUsername、passwordReset、selfRegistration：未声明 role，属于找回用户名、密码重置和注册流程；结合实例配置中的 forgotUsername=false、forgotPassword=false、selfRegistration=false，它们不是当前可用的管理入口。

个人资料页可以打开，我当时主要查看它调用的 API，没有提交资料或密码修改。

补充笔记：参数测试如何做对照

这次 JATO 测试同时改了对象内容和参数位置，难以分清响应差异的来源。后续做类似验证，可以先固定入口、请求方法、会话和参数位置，每轮只改变一个因素；再单独比较 Query 与 POST。这样得到的差异才更容易解释。

除了状态码，还应比较响应体和错误信息，并保留正常请求作基线。某个字段被回填或被清空，不能直接推出内部调用成功，也不能替代命令执行证据。这是对本次测试方法的复盘，不代表当时已经完成了全部控制变量测试。
