[HTB] Paperwork 渗透测试笔记

发表于2026-11-12|更新于2026-11-12|htb
|总字数:2.9k|阅读时长:10分钟|浏览量:

这次打的是 HTB 的 Paperwork（Easy / Linux）。
从 Web 页面提供的打印服务线索出发，依次经过 LPD 命令注入、PJL 路径穿越与 SSH 公钥写入，最后通过 Unix socket 泄露的文件描述符取得 root 权限。
按实际发现顺序记录 Hack The Box 授权靶场中的验证过程。

路径概览

已验证的关键节点

01 · LPD 源码

Web 页面给出 RFC 1179、队列名和 Python 下载文件；控制文件中的 J 字段最终进入 shell=True。

02 · lp shell

按服务端的实际读取方式提交控制文件，先以 HTTP 回连证明命令执行，再获得 lp shell。

03 · PJL 文件读写

从本地 JetDirect/PJL 服务读取日志和 user.txt，再经路径穿越写入 archivist 的 SSH 公钥。

04 · SCM_RIGHTS 泄露

审计 root daemon，接收其错误传递的敏感文件描述符，取得可用于 su - 的实验口令。

一、初始侦察

1. 端口扫描

初始扫描显示 22/tcp、80/tcp 与 1515/tcp。Nmap 将 1515 猜测为 ifor-protocol?，这只表示指纹库没有准确识别服务，不能据此确定真实协议。

2. Web 页面与 LPD 线索

访问 http://paperwork.htb/ 后，页面给出了更可靠的线索：

  • Compliance Level: RFC 1179；
  • 目标队列 archive_intake；
  • 可下载的内部处理器 paperwork-archive-v1.02。

RFC 1179 对应 Line Printer Daemon（LPD）。1515 不是标准 LPD 端口 515，且服务是自定义 Python 实现；因此 RFC 只用来理解报文结构，最终行为仍以源码和响应为准。

2. 构造无害控制文件并观察 ACK

服务端将首字节 2 作为“接收打印任务”主命令，将剩余文本解析为队列名。队列 archive_intake 被接受后，下一阶段接收控制文件的子命令、字节长度与文件名。

长度必须是控制文件的 bytes 长度，不能凭字符数估算。控制文件头返回 0x00 ACK，正文后又返回两个 0x00；随后服务端仍等待后续数据，客户端以超时结束读取。该现象与源码中 ACK 后继续 recv() 的逻辑一致。

4. 验证 root 认证并读取 root.txt

配置中的 ADMIN_PASSWORD 在该实验环境中可用于 root 本地认证。执行 su - 后，whoami 返回 root，并可读取 root.txt。

七、总结与复盘

观察能证明什么不能直接证明什么
1515 被 Nmap 识别为未知服务指纹库未准确命名该服务它一定是 IFOR 或任何其他协议
页面写有 RFC 1179 与队列名LPD 是有依据的调查方向该服务完整实现了 RFC
J 字段的 HTTP 回连可控数据进入 shell 并执行 curl所有 LPD 服务都有命令注入
FSUPLOAD 0:/../user.txt 成功PJL 路径未被限制在 printer 根目录所有系统路径都可读写
mgmt.sock 为 root:archivist、权限 660archivist 可以连接 socket必然能读取任意 root 文件
recvmsg() 收到 admin_fddaemon 泄露了该已打开文件的读取能力archivist 获得了普遍 root 文件访问权

本次需要分别检查协议输入与执行命令、访问文件等敏感操作之间的数据流：本机存在 shell 拼接、路径约束缺失，以及高权限 FD 错误委派三种实现缺陷。

防护上，LPD 服务不应使用 shell=True 拼接控制文件数据；PJL 文件操作应对 realpath 结果执行根目录包含性检查；管理 daemon 不应向低权限客户端传递敏感 FD，并应在 Unix socket 上实施明确的请求认证和最小权限组授权。
