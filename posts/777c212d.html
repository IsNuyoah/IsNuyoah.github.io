用 Azure 香港服务器做 WireGuard 出口：Windows 11 的配置与实测

发表于2026-11-19|更新于2026-11-22|网络技术
|总字数:2.9k|阅读时长:11分钟|浏览量:

之前用的节点不太稳定，练靶场时经常被网络打断。正好当时通过 GitHub 学生认证领到了 100 美元的 Azure 额度，我就在香港开了一台 Ubuntu 虚拟机，用 WireGuard 给自己的 Windows 11 做 IPv4 出口。

第一次看到 WireGuard 的握手时间时，我只给服务端的隧道地址配了路由。这时能 ping 通香港的 Ubuntu，浏览器却仍走原来的出口。后来真正让我确认转发生效的，是从 Windows 发出的 HTTPS 请求：公网服务返回了这台 Azure 虚拟机的公网 IP。

这次没留下操作截图，先把配置、命令和实测结果记下来，等以后换节点时再补图。

一次请求怎么走

下文用 __名称__ 标记需要按部署填写的值。配置、命令和附录脚本中的同名标记使用同一个值，运行前请先替换。

配置项配置值
Azure 区域与系统香港（East Asia），Ubuntu 24.04
Windows 连接的公网端点__SERVER_PUBLIC_IPV4__:__WG_PORT__（UDP）
服务端主机名__SERVER_HOSTNAME__
Windows 隧道名__WINDOWS_TUNNEL__
服务端隧道接口__WG_IFACE__，地址 __SERVER_TUNNEL_IPV4__/__PREFIX_LEN__
Windows 隧道地址__CLIENT_TUNNEL_IPV4__/32
Ubuntu 出口__EGRESS_IFACE__，网卡私网地址 __SERVER_PRIVATE_IPV4__
隧道 DNS 服务器__DNS_IPV4__

Endpoint 告诉 Windows 去哪里找 WireGuard 服务端，所以这里填 Azure 公网地址和 UDP 端口。握手后，ping 的目标则是服务端的隧道地址。Ubuntu 出口网卡上的私网地址只在 Azure 虚拟网络内使用。

Windows 的流量什么时候开始走香港

我在 Windows 的 [Peer] 中分三次设置 AllowedIPs，每次扩大范围后都从 Windows 发起一次测试。

Windows 端的 AllowedIPs测什么当时看到的结果
__SERVER_TUNNEL_IPV4__/32ping 服务端隧道地址5 发 5 收，平均 105 ms
__SERVER_TUNNEL_IPV4__/32, 1.1.1.1/32通过 HTTPS 访问 1.1.1.1返回的 ip= 与 Azure 公网 IPv4 一致
0.0.0.0/0用浏览器访问测试路由以外的站点错误页显示了同一个 Azure 公网 IPv4

这里的 /32 只匹配一个 IPv4 地址，0.0.0.0/0 覆盖整个 IPv4 地址空间。三次调整都发生在 Windows 上；服务端为这个客户端保留的始终是 __CLIENT_TUNNEL_IPV4__/32。

最近一次握手说明两端已完成认证，ping 收到回复则验证了隧道内的 IPv4 往返。当时的 105 ms 是五次往返的平均值；要评估练靶场时关心的长期稳定性，还需要更长时间的丢包和延迟记录。

当天我也从服务端反向 ping 过 Windows。为做这项测试，我在 Windows 防火墙里临时允许了来自服务端隧道地址的 ICMP 请求；日常上网无需这条规则。

验证转发：只让一个公网地址走香港

让 Ubuntu 成为出口，需要同时满足三个条件：内核开启 IPv4 转发，防火墙允许客户端发出的转发流量及对应回包，出口网卡对客户端地址做 MASQUERADE。这台机器用 __EGRESS_SERVICE__.service 随 WireGuard 加载规则，并限制隧道转发到私网、链路本地地址及 Azure 平台地址。新建同布局节点时，可参考文末配置附录。

我的两项服务均返回 active，net.ipv4.ip_forward 为 1。NAT 规则匹配源地址 __CLIENT_TUNNEL_IPV4__/32 和出口 __EGRESS_IFACE__，路由查询也指向 __EGRESS_IFACE__。

切换 Windows 默认 IPv4 出口

单地址测试通过后，我在 Windows 隧道中改了两项：

Windows 配置段最终值作用
[Interface]DNS = __DNS_IPV4__为隧道指定 DNS
[Peer]AllowedIPs = 0.0.0.0/0默认 IPv4 流量走香港节点

我在 Windows 客户端保留了「阻止非隧道流量」，保存配置后重新连接。这套配置只提供 IPv4 出口，启用阻断后，普通 IPv6 公网连接也会受到限制。

重连后，在 Windows 运行开头的出口查询命令。这次换用 api.ipify.org，因为前一阶段只给 1.1.1.1 单独加过路由；继续测原地址无法区分是哪条路由生效。查询的预期结果是同一个香港公网 IPv4。

当时浏览器打开的是站点错误页，但错误页也留下了一条可核对的证据：页面显示的客户端 IP 与 Azure 公网 IPv4 一致。到这里，我确认了这次 Windows 浏览器请求的出口。靶场虚拟机有自己的网络配置，它的出口还要在虚拟机内单独验证。

遇到问题时从哪一层查

现象下一步检查
已点连接，一直没有最近握手对照两端公钥、Azure 公网地址、UDP 监听端口及实际生效的网络安全组规则。
能 ping 通隧道地址，单地址 HTTPS 测试超时先看 Windows 的测试路由是否包含 1.1.1.1/32，再对照 Ubuntu 的转发开关、FORWARD 和 NAT 规则。
直接访问 IP 成功，切换后访问域名失败在 Windows 执行 Resolve-DnsName api.ipify.org -Type A，把 DNS 解析失败和后续 HTTPS 错误分开检查。
网站显示错误页，但页面上的出口 IP 正确记录站点返回的具体错误，再查站点自身的可用性。出口 IP 和页面状态回答的是两个不同的问题。
