[THM] Lookup 渗透测试笔记

发表于2026-11-19|更新于2026-11-19|thm
|总字数:2.1k|阅读时长:6分钟|浏览量:

Lookup 攻击链

登录页 · 账号识别

密码相同，换个用户名，登录页就给出了不同的报错。这条线索最终带我进入了 elFinder 文件管理站点。

Web 服务 · www-data

在 elFinder 测试中，命令回显给出了服务账户 www-data 的身份，随后监听端收到了初始 Shell 连接。

用户会话 · think

自定义 SUID 程序暴露了口令线索。我通过 SSH 登录 think，读取了家目录中的 user.txt。

管理员会话 · root

think 的 sudo 授权使受限文件可读。随后，我在新的 SSH 会话中确认了 root 身份，并读取了 root.txt。

靶机信息

项目本次记录
平台与房间TryHackMe · Lookup
初始目标 IP10.144.145.103
后续 SSH 截图中的目标 IP10.144.156.105
完成情况已读取 user.txt 和 root.txt

端口扫描与 Web 入口

初始实例的 Nmap 扫描发现两个开放的 TCP 端口。22 端口运行 OpenSSH 8.2p1，80 端口运行 Apache 2.4.41。让我先去看 Web 的是 HTTP 标题探测那一行：服务器把请求重定向到了 http://lookup.thm。

在本机的 /etc/hosts 中配置域名解析后，浏览器打开了登录页。开发者工具里的表单写着 action="login.php" 和 method="post"，可以直接对照提交前后的页面。

两次失败登录，两个不同的提示

第一次输入用户名和密码 1/1，页面显示 Wrong username or password.，三秒后跳转。

随后尝试 admin/admin，提示变成了 Wrong password. Please try again.。同一个表单对用户名作了区分，admin 因此成为第一个值得核对的账号。

用小字典跑 ffuf 时，我起初把响应长度过滤值设成了 103。看终端结果才发现，大多数名字返回 74 字节，admin 返回 62 字节，两类响应的 HTTP 状态码都是 200。

第二次换用较大的名字字典，并按实测的 74 字节过滤。剩下的 admin 和 jose 都返回了 62 字节。

后续验证中，jose 的一组凭据收到了 HTTP 302。用浏览器登录后，目的地址变成了 files.lookup.thm，至此才确认这个账号能够进入另一个站点。

文件管理站点与 elFinder 版本

浏览器访问子域名时，本机也需要能解析 files.lookup.thm。这和 HTTP 虚拟主机的选择分属两个环节：域名解析决定连接哪个 IP，请求中的 Host 字段供 Web 服务器选择该地址上的站点。本次子域名来自登录后的跳转。

进入 elFinder 后，文件列表里许多项目带有锁形标记。打开 credentials.txt，窗口里只有一行 think : nopassword。这是 think 第一次出现在记录中，当时还没有登录结果能验证这行文字。

我把文本文件下载到本地查看，也从前端 JavaScript 中找到了版本字符串 2.1.47。

elFinder 的 About 窗口同样显示 2.1.47，与脚本里的版本一致。

两次上传分别被什么拦下

先尝试上传 PHP 文件。界面返回 File type not allowed. (application/x-php)，错误框明确点出了文件类型。

接着尝试上传 .htaccess。这次错误变成了 Invalid file name.。两次上传都失败了，但第二次只能确认这个文件名被拒绝；仅凭这张图，还无法断定所有以点开头的文件都受同一条规则限制。

从版本记录到初始会话

按版本检索公开漏洞记录后，SearchSploit 列出了 elFinder PHP connector 的命令注入条目。至此确认的是版本与条目相符，目标上的执行结果还需要单独验证。

我按公开样例修改了本地测试脚本。终端回显中出现 uid=33(www-data) 和 gid=33(www-data)，这给出了服务端执行命令时使用的身份。

随后监听端收到了连接，工作目录位于 elFinder 的 PHP 目录。终端同时提示缺少作业控制，这也是后面调整交互终端的原因。

从 www-data 到 think

查看 /home/think 时，.passwords 和 user.txt 的属主、属组都是 root:think，权限均为 -rw-r-----。当前会话的身份是 www-data，两份文件的权限都没有向其他用户开放读取。

接下来检查带 SUID 位的文件。结果里有不少系统工具和 Snap 路径，另外还有一个自定义程序 /usr/sbin/pwm。

pwm 的属主是 root，所有者执行位显示为 s。程序字符串里同时出现了读取 id 输出的提示和路径模板 /home/%s/.passwords。截图底部的跟踪输出只显示 pwm 自身启动；外部命令的查找方式还要结合后面的行为判断。

在后续测试中，改变 pwm 取得的用户名后，程序输出了 think 的候选口令。问题出在权限与输入来源的组合：程序有权读取受限文件，却用调用者能影响的身份信息决定读取谁的文件。

传回本地的文件共有 51 行。SSH 验证记录显示其中一条凭据有效，对应用户为 think。

SSH 登录后，whoami 返回 think。这次会话可以读取家目录里的 user.txt，与此前看到的文件属组和权限一致。

从 think 到 root

检查 think 的 sudo 权限时，发现它可以用 root 身份运行 /usr/bin/look。这个工具会把指定文件中匹配前缀的行写到终端；一旦以 root 身份读取，输出就可能包含普通用户无权查看的内容。

终端提示 [sudo] password for think: 时，我输入了此前在 SSH 口令测试中确认的 think 密码。认证通过后，look 的输出中出现了 OpenSSH 私钥头。

随后用这把密钥连接后续实例，终端显示 Ubuntu 登录横幅和目标地址 10.144.156.105。

最后在远端执行 whoami，输出为 root；当前目录中可见 root.txt，文件也能正常读取。

总结与复盘

观察能证明什么不能直接证明什么
两类失败登录都返回 200，正文分别为 74 和 62 字节固定测试密码后，用户名会影响错误响应较短的响应意味着认证成功
PHP 文件触发文件类型错误，.htaccess 触发文件名错误两次上传被拒时，服务给出了不同原因服务会拦截所有脚本或所有点号开头的文件
elFinder 的 About 页面和前端脚本均显示 2.1.47两处可见的版本信息一致仅凭版本就能确认服务端命令执行
测试回显为 www-data，随后监听端收到交互连接初始命令执行的身份和会话建立各有证据初始会话已有 think 的文件读取权限
pwm 字符串中出现用户名和密码文件路径，随后测试取得候选口令字符串给出了调查方向，运行结果验证了受限数据可被读出字符串本身足以还原程序运行时的每一次调用
look 输出私钥头，后续 SSH 会话中 whoami 返回 root敏感文件读取和 root 登录分别得到了验证读取文件时就已经取得了交互式 root shell

回看登录阶段，最值得保留的是同一轮请求的对照。103 是当时填入的过滤值，74 和 62 才是终端实际记录的响应长度。到了权限阶段，同样要看输出来自哪个进程：文件内容出现在终端，说明读取成功；远端会话里的身份回显，才说明登录后是谁。

防护上，登录接口应对未知账号和错误密码使用一致的失败响应。高权限程序应从可信来源取得调用者身份，并限制可读取的文件范围。审查 sudo 授权时，也要把工具能够输出的敏感内容计入它实际获得的权限。
