[THM] Overpass 2 Hacked 流量分析与后门溯源

发表于2026-11-04|更新于2026-11-07|thm
|总字数:2.9k|阅读时长:10分钟|浏览量:

Overpass 生产环境遭到入侵。该题提供了攻击发生时捕获的 PCAP，目标是从网络证据重建攻击路径，并在重新部署的靶机上验证攻击者遗留的访问方式。
本文按实际发现顺序整理。

路径概览

已验证的攻击与验证链

01 · PHP 文件上传

从 HTTP POST 中定位 /development/upload.php，恢复上传的 payload.php。

02 · 反连 Shell 取证

根据 payload 中的 192.168.170.145:4242 聚焦 TCP stream，重建攻击者的明文交互命令。

03 · 历史提权与后门部署

流量证明攻击者切换至 james、读取 /etc/shadow，随后部署伪装 SSH 服务并监听 2222。

04 · 密码派生逻辑与后门验证

根据 Go 源码确定 SHA-512(password + salt)，离线恢复后门口令并连接 2222。

05 · SUID Bash 提权

在 james 家目录发现 root-owned SUID Bash，以保留有效 UID 的方式获得 root shell。

源码逻辑：认证算法与会话行为

以下结论来自题目流量中攻击者克隆的项目源码；这里只分析认证和会话逻辑。

启动配置与运行时 hash

main 的默认配置包括：监听 0.0.0.0:2222、伪装 banner OpenSSH_8.2p1 Debian-4、读取 id_rsa 作为服务端 host key，以及一个可被 -a/--hash 覆盖的全局 hash。PCAP 中的 ./backdoor -a <runtime-hash> 因此覆盖了源码里的默认值；后续认证应以流量中传入的 runtime hash 为准，而不是源码默认 hash。

认证调用链可概括为：

passwordHandler 的 ssh.Context 参数被命名为 _，即用户名等 context 信息不参与此函数的认证判断；它只校验密码。源码使用的是固定 salt 的单次 SHA-512，而不是慢速 KDF 或标准 sha512crypt。salt 不是秘密，但硬编码和单次哈希会使获得 hash 的攻击者能够高效离线猜测口令。

源码还表明 sshterminal 在认证成功时以 /bin/bash -i 提供交互会话，并检查是否请求 PTY；未请求 PTY 时会返回 No PTY requested.。虽然项目中定义了 sshHandler 与 runCommand，但 Server{ Handler: sshterminal } 实际注册的是 sshterminal，所以不应把 runCommand 当成本次已证实的执行路径。

验证 2222 后门与 user 阶段

将恢复出的后门密码用于 2222 端口后，服务端接受认证并进入 james 的家目录；目录中可见攻击者克隆的 ssh-backdoor 项目、host key 和构建文件。由 shell 提示符不足以证明身份，后续以读取 user flag 和本地文件权限作为补充证据。

最终提权：当前实例中的 SUID Bash

james 家目录的 ls -la 显示了一个不同寻常的文件：

关键证据是 owner 为 root 且权限位中包含 s。这表示该 Bash 副本带有 root SUID；执行时可获得有效 UID 0。以保留特权模式启动后，whoami 返回 root，并成功读取 /root/root.txt。它构成可用于本地提权和持久化的高风险后门，而不是 sudo 密码爆破结果。

该文件位于攻击链关联用户 james 的家目录，且当前实例中与后门访问一同出现，因此与攻击遗留物一致；但现有 PCAP 截图没有捕获创建 .suid_bash 的命令，不能仅凭文件存在断言其创建者或创建时间。

两个 Flag 均已取得。 入口是 PCAP 中恢复的 SSH 后门认证链；最终 root 来自当前实例中 root-owned SUID Bash 的实际执行。

SOC 视角：可检测的攻击痕迹

阶段网络或主机证据可支持的结论
初始访问POST /development/upload.php、payload.php、application/x-phpWeb 上传端点接收了 PHP 文件
命令控制到 192.168.170.145:4242 的 Netcat 反连流会话内容在捕获中明文可见
权限扩大su james、sudo -l、sudo cat /etc/shadow攻击者获得 james 并在当时读取 shadow
后门部署git clone ssh-backdoor、ssh-keygen、chmod +x、监听 2222新的伪装 SSH 服务被部署
持久化/最终提权root-owned .suid_bash 且带 SUID 位本地用户可借该文件获得有效 root 权限；创建者与创建时间仍待其他证据确认

本题最重要的取证习惯是将“PCAP 中曾发生的行为”和“重新部署靶机上实际验证的行为”分开写：历史流量给出攻击路径和配置线索；端口扫描、后门登录、文件权限与 whoami 则确认这些线索在当前实例中的实际影响。

总结与复盘

这次最有价值的不是单独获得一个 shell，而是把一份 PCAP 中的零散证据还原为可验证的攻击链：PHP 上传建立 www-data 反连 Shell，攻击者切换到 james 并读取 shadow，部署伪装 SSH 服务，最后在当前实例中通过 SUID Bash 获得 root。

复盘点本次得到的结论
从宽到窄分析流量先以 HTTP 请求和 POST 过滤流量，再检查 multipart 字段与文件内容，能避免在大量 ARP、DNS、mDNS 等噪声中直接手工翻包。
以完整会话而非单包归因上传请求本身只证明文件进入端点；将 payload 中的回连地址、4242/TCP stream 和 uid=33(www-data) 连起来，才形成初始访问的证据链。
分开看不同凭据james 的系统账户密码、/etc/shadow 中的账户哈希、SSH 后门的自定义认证密码不是同一类材料。一个凭据在某处成功，不等于可用于所有服务。
用源码决定哈希模式后门 hash 是 SHA-512(password + salt)，而不是无 salt 的 Raw SHA-512。运行命令中的 -a 还覆盖了源码默认 hash；只有源码、运行参数和 Hashcat 模式三者一致，离线审计结果才有意义。
权限结论需要运行证据看到 SUID 位只能提出提权假设；whoami=root 和成功读取 /root/root.txt 才证明该文件在当前实例中实际获得了 root。

本次过程中，multipart payload 的导出以及 sha512($pass.$salt) 对应 Hashcat mode 1710 的选择使用了明确指导。因此这些步骤应视为依据已知证据完成的复现验证。2222 后门连接和 SUID Bash root 验证保留实际操作与输出作为证据。
